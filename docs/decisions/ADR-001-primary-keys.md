# ADR-001. Тип первичного ключа

**Статус:** принято

## Контекст
У каждой вакансии, города и неанонимного работодателя есть id на hh.ru (строка из цифр: `"104857600"`). Нужно решить, что будет первичным ключом в нашей базе.

**Вопрос:** «Можем ли мы гарантировать, что id источника никогда не изменится и всегда будет?»

## Варианты
1. **Натуральный ключ** — использовать `hh_id` как PRIMARY KEY.
2. **Суррогатный ключ** — свой `BIGINT GENERATED ALWAYS AS IDENTITY` + `hh_id UNIQUE NOT NULL`.
3. **UUID** — случайный 128-битный id.

## Решение
Вариант 2: суррогатный `id BIGINT` + уникальный `hh_id TEXT`.

## Почему
- Внешний id не под нашим контролем: источник может изменить его формат или правила выдачи.
- Анонимных работодателей в `employer` не пишем (у вакансии `employer_id = NULL`), поэтому на выбор ключа они не влияют.
- Если появится второй источник (например, SuperJob), id двух источников могут совпасть. Тогда уникальный ключ станет `(source, hh_id)`, а внешние ключи не изменятся: они ссылаются на суррогатный `id`.
- `BIGINT` занимает 8 байт и быстро сравнивается. Внешние ключи в `vacancy_skill` и `vacancy_snapshot` компактнее, чем текстовые.
- UUID нужен, когда id генерируют несколько независимых систем без общей базы. У нас одна база — UUID дал бы только лишние 16 байт и неудобные для чтения id.
- `hh_id` храним как `TEXT`, а не число: API отдаёт строку, и мы не обещаем, что там всегда будут только цифры.

## Последствия
- (+) Новый источник меняет только уникальный ключ и добавляет колонку `source`; внешние ключи остаются прежними.
- (−) Нужна дополнительная уникальность на `hh_id` и лишний индекс.
- (−) При загрузке нужно сначала узнать наш `id` по `hh_id` (`RETURNING id` решает это одним запросом).
